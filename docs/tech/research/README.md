# Tech Research Index

Fourteen research threads (2026-09-05 through 2026-09-06), each assessing: existing solutions, technical viability, implementation options, and a concrete build recommendation. Threads 01–07 cover the major system components; 08–10 answer specific open questions raised across [idea/17](../../idea/17-meeting-notes-tree-simplification.md), [18](../../idea/18-meeting-notes-feature-ranking.md), [20](../../idea/20-meeting-notes-input-modes.md), and [09-open-questions.md](../../idea/09-open-questions.md) — see [idea/19-open-questions-resolved.md](../../idea/19-open-questions-resolved.md) for the consolidated answers across *all* open questions, researched and reasoned-through alike. 11–14 answer four voice-memo-raised GitHub issues ([idea/24](../../idea/24-meeting-notes-onboarding-entry-and-accessibility.md), [25](../../idea/25-meeting-notes-caregiver-training-mode.md), [26](../../idea/26-meeting-notes-voice-vocabulary-calibration.md), [27](../../idea/27-meeting-notes-visual-field-loss.md)). These are research briefs, not decisions — see [../README.md](../README.md) for what's actually been decided, and fold anything actionable back into the `idea/` docs as the team locks choices.

| # | Thread | Headline verdict |
|---|---|---|
| [01](01-input-methods.md) | Touch/switch input calibration & fallback | **Strong.** Buttons/joystick/trackpad are all trivial in Flutter (mostly no packages needed); the scoring formula is legitimate but needs fixed normalization ceilings + small-N safeguards; no shipped product does multi-method calibration + auto-fallback the way this project proposes — that's real differentiation, not a gap. |
| [02](02-speech-recognition.md) | Speech recognition for atypical/dysarthric & Indian-language speech | **Mixed.** Full personalized-ASR fine-tuning (Euphonia/Voiceitt-style) is real but not buildable in 30h. The right-sized version of the "call amma" training loop is a small enrolled-phrase matcher (few-shot keyword spotting or fuzzy match), which is genuinely buildable. VAD for the `sounds` tier is solved and trivial. Google Cloud STT is the safe default for Hindi; Sarvam AI is the better-fit but less-tested option for code-switching. |
| [03](03-proactive-narration.md) | Proactive/context-aware narration output | **Moderate for the full vision, Strong for a scoped version.** No existing tool does "proactively watch app state + salience-filter + minimal spoken narration" — genuinely novel combination. Build request/response narration first (cheap, reuses the same LLM+accessibility-tree pipeline already planned); layer proactive polling on top only if time remains, hard-coded to the one demo scenario. |
| [04](04-agent-execution-layer.md) | AI agent execution layer (OpenClaw vs. alternatives) | **Strong recommendation to drop OpenClaw.** A hand-written ~150–300 line loop (Playwright accessibility snapshot → LLM tool-call → confirm → dispatch) is simpler, safer, and equally buildable — avoids OpenClaw's documented CVEs and broad shell/filesystem attack surface for a task that needs none of it. Accessibility-tree targeting is also empirically more reliable than pixel-based targeting for well-structured markup (both demo surfaces qualify). |
| [05](05-mobile-remote-architecture.md) | Flutter phone ↔ agent backend architecture | **Strong for the lean stack.** Raw WebSocket (no Firebase/Supabase needed — the agent backend is already a server process), `flutter_joystick` + hand-rolled trackpad + `speech_to_text` + `flutter_tts`, `shared_preferences` with one JSON blob for the profile. Biggest risk: the phone↔backend message schema must be nailed down before either side builds deep into it. |
| [06](06-competitive-deep-dive.md) | Competitive/prior-art deep dive (beyond existing market research) | **Real prior art found — reframes the differentiation claim.** Google's "Natively Adaptive Interfaces," a May 2026 arXiv paper formalizing an almost-identical continuous capability-axis model, and the older EU GUIDE project all narrow what's safely claimable. Nothing found combines all three of (a) a live per-user profile, (b) runtime partial-modality fusion, and (c) an AI agent executing + inferring under a confirmation gate — that three-way combination, plus the explicit precision–inference coupling law, is the defensible claim. |
| [07](07-dasher-integration.md) | Dasher (github.com/dasher-project/dasher) integration | **Cite as prior art; don't integrate.** Dasher is real, decades-old, actively maintained upstream (at `GNOME/dasher` — the linked repo is a stale 2023 fork), with a WASM port that its own maintainers call "a demo, not a supported product." It's strong, specific evidence for a real gap this project hasn't addressed (free-text entry for users with no reliable speech *and* no reliable tap) — flagged as a roadmap item, not build scope. |
| [08](08-feature-ranking-auxiliary-tree.md) | Feature ranking & "auxiliary tree" generation, without an LLM per decision | **Strong.** Ranking accessibility-tree nodes by landmark role, heading level, interactivity, and link density (Readability.js/Boilerpipe-style, zero ML) mirrors exactly how real screen-reader users already navigate (~72% via headings, per WebAIM). Recommends a two-tier system: heuristic scorer first, a single narrow LLM call only when the heuristics are genuinely ambiguous. New-page detection is a solved problem (History API interception + MutationObserver fallback); "unknown" elements are resolved by watching the post-interaction effect, not classifying the element. |
| [09](09-vision-calibration.md) | Vision calibration method | **Strong for a scoped hybrid.** Real prior art exists (Peek Acuity, MNRead) but is more than a hackathon needs. Recommends 2–3 shrinking-text steps run *after* touch calibration (reusing the already-calibrated target size to avoid the vision test failing for touch-precision reasons instead of vision reasons), confirmed via a full-width tap zone or the `sounds` speech tier. |
| [10](10-additional-input-modes.md) | Additional input modes beyond touch/speech/switch-scanning (gaze, head-tracking, sip-and-puff, EMG, non-invasive BCI, grid-based voice) | **Weak-to-Moderate feasibility, all roadmap not build-scope.** Gaze and head-tracking are real 2025–2026 research directions using only a phone's front camera (no extra hardware) but need their own calibration surface — good 5th/6th-method roadmap candidates. Sip-and-puff, EMG, and non-invasive BCI all need external hardware a stock phone doesn't have — citation-only. The meeting's "grid-based voice input" idea already ships today as Android Voice Access's "show numbers"/"show grid" overlay — clone that pattern rather than designing from scratch. Every mode surveyed converges on the same coarse-select-then-fine-confirm shape already used in thread 01's fallback matrix. |
| [11](11-accessible-entry-onboarding-and-contrast.md) | Accessible entry/onboarding bootstrapping, high contrast, screen-reader announcement, recorded voice vs. TTS ([GH #1](https://github.com/saranskumar/startathon/issues/1)) | **Strong, mostly additive.** Android/iOS both solve the "how does a limited user trigger setup" problem with a fixed, content-independent physical gesture, not a precision-gated button — copy that shape for the entry screen. High contrast and screen-reader support (Flutter `Semantics`/`liveRegion`, not ARIA) are standard, well-specified builds. Recorded onboarding voice over TTS is defensible for small fixed content specifically, not a general TTS-is-worse finding — research is genuinely mixed and modern TTS narrows the gap. Progressive input levels turned out to be an internal architecture question (does the profile stay one-shot?), not an external research one. |
| [12](12-caregiver-guided-training-mode.md) | Caregiver-guided pre-calibration training mode ([GH #2](https://github.com/saranskumar/startathon/issues/2)) | **Strong — this is an established technique, not a new one.** The proposed idea is "physical prompting" (hand-over-hand/hand-under-hand), a named OT/ABA technique with direct evidence it improves motor-skill acquisition. Recommends hand-under-hand as the gentler default and structuring the mode around ABA's most-to-least prompt-fading sequence (full physical → partial physical → prompted-independent → calibration) rather than open-ended repetition, plus surfacing the real consent/dignity consideration the source literature treats as inseparable from the technique. |
| [13](13-sentence-based-voice-vocabulary-calibration.md) | Sentence-based voice vocabulary calibration & dynamic word-choice input ([GH #3](https://github.com/saranskumar/startathon/issues/3)) | **Strong, buildable extension of already-scoped work**, targeting specifically the population between the `full`/`partial` free-dictation tier and the tone/noise-based `sounds` tier. Multi-sentence elicitation with embedded target words, difficulty-ordered by syllable/phonetic complexity, matches established dysarthria therapy progressions and ASR semi-text-dependent enrollment research. The resulting per-word personal vocabulary reuses the few-shot/fuzzy-matching approach already recommended in [02](02-speech-recognition.md). One correction: use fixed carrier sentences with the target word in a known slot, not fully free sentences, to keep target-word scoring tractable. Option mapping is two modes, not one: direct mapping for small option counts, and a fixed next/previous/select mapping (independent of option labels) for large ones — the second mode resolves the arbitrary-label gap flagged in an earlier draft by reusing the cycling fallback pattern already specified in [03 §3.3](../../idea/03-input-calibration.md). |
| [14](14-visual-field-loss-tunnel-and-peripheral-vision.md) | Visual field loss — tunnel vision & central/peripheral-only vision ([GH #4](https://github.com/saranskumar/startathon/issues/4)) | **Real, well-documented, and the two named conditions are opposites needing opposite fixes.** Tunnel vision (retained central, lost peripheral field) needs condensed single-column layout with spatial continuity between task steps — validated by W3C low-vision guidance and a tunnel-vision-simulation case study, and matches the idea's own instinct exactly. Central/peripheral-only vision (e.g. macular degeneration, retained peripheral, lost central) needs the opposite: single-line scrolling text (the shipped MD_evReader/EV News pattern) and avoiding small centered-only targets, with high contrast as a secondary lever, not the primary fix. Needs its own field-mapping calibration test, but one that reuses the touch axis's existing grid-point mechanism. Roadmap, not event scope. **Current app: tunnel overlay being removed; later layout puts all controls inside one square** ([app/04](../../app/04-clarity-playground-and-field.md)). |
| [15](15-google-nai-comparison.md) | Google Natively Adaptive Interfaces (NAI) — detailed comparison, follow-up to [06](06-competitive-deep-dive.md) §1.1 | **NAI is an LLM-orchestrated (Gemini) research framework/prototype line (StreetReaderAI, MAVP) with no explicit persistent capability profile — adaptation is implicit in the model, not a measured, inspectable data structure.** Written specifically against the team's decision to use zero AI ([idea/28](../../idea/28-meeting-notes-scope-lock-no-ai.md)): the comparison sharpens rather than weakens once AI left this project's build — deterministic, auditable, free-to-run capability-profile system vs. NAI's per-interaction LLM-mediated adaptation. |

## Cross-cutting themes worth folding back into `idea/`

- **The "no shipped product does X" pattern repeats across threads 01, 05, and 06** — independently confirms the composition/fallback/profile-driven mechanism is real differentiation, not just under-researched. Worth stating in the pitch with this evidence behind it.
- **Threads 02, 03, and 04 all converge on the same build principle**: don't build the maximal/research-grade version (full ASR personalization, fully general proactive narration, a general agent framework) — build the scoped-down version that reuses infrastructure already committed to elsewhere (the accessibility-tree + LLM pipeline), and treat the maximal version as roadmap.
- **Thread 06 changes a claim already in the pitch**: "no one models users on continuous ability axes" is no longer safe to say unqualified — a May 2026 paper already formalizes nearly the same model. The correct claim is narrower and, per that thread's finding, still fully defensible: nobody combines the profile *with* runtime fusion *and* an inferring, confirmation-gated execution agent.
- **Thread 07 exposes a real gap**, not just a citation opportunity: the current design assumes voice carries all free-text content, which leaves users with neither reliable speech nor reliable discrete tapping unaddressed — exactly Dasher's original use case. Worth a line in [idea/09-open-questions.md](../../idea/09-open-questions.md) or the roadmap.

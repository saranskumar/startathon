# Tech Research Index

Nine research threads (2026-09-05), each assessing: existing solutions, technical viability, implementation options, and a concrete 30-hour-build recommendation. Threads 01–07 cover the major system components; 08–09 answer specific open questions raised across [idea/17](../../idea/17-meeting-notes-tree-simplification.md), [18](../../idea/18-meeting-notes-feature-ranking.md), and [09-open-questions.md](../../idea/09-open-questions.md) — see [idea/19-open-questions-resolved.md](../../idea/19-open-questions-resolved.md) for the consolidated answers across *all* open questions, researched and reasoned-through alike. These are research briefs, not decisions — see [../README.md](../README.md) for what's actually been decided, and fold anything actionable back into the `idea/` docs as the team locks choices.

| # | Thread | Headline verdict |
|---|---|---|
| [01](01-input-methods.md) | Touch/switch input calibration & fallback | **Strong.** Buttons/joystick/trackpad are all trivial in Flutter (mostly no packages needed); the scoring formula is legitimate but needs fixed normalization ceilings + small-N safeguards; no shipped product does multi-method calibration + auto-fallback the way this project proposes — that's real differentiation, not a gap. |
| [02](02-speech-recognition.md) | Speech recognition for atypical/dysarthric & Indian-language speech | **Mixed.** Full personalized-ASR fine-tuning (Euphonia/Voiceitt-style) is real but not buildable in 30h. The right-sized version of the "call amma" training loop is a small enrolled-phrase matcher (few-shot keyword spotting or fuzzy match), which is genuinely buildable. VAD for the `sounds` tier is solved and trivial. Google Cloud STT is the safe default for Hindi; Sarvam AI is the better-fit but less-tested option for code-switching. |
| [03](03-proactive-narration.md) | Proactive/context-aware narration output | **Moderate for the full vision, Strong for a scoped version.** No existing tool does "proactively watch app state + salience-filter + minimal spoken narration" — genuinely novel combination. Build request/response narration first (cheap, reuses the same LLM+accessibility-tree pipeline already planned); layer proactive polling on top only if time remains, hard-coded to the one demo scenario. |
| [04](04-agent-execution-layer.md) | AI agent execution layer (OpenClaw vs. alternatives) | **Strong recommendation to drop OpenClaw.** A hand-written ~150–300 line loop (Playwright accessibility snapshot → LLM tool-call → confirm → dispatch) is simpler, safer, and equally buildable — avoids OpenClaw's documented CVEs and broad shell/filesystem attack surface for a task that needs none of it. Accessibility-tree targeting is also empirically more reliable than pixel-based targeting for well-structured markup (both demo surfaces qualify). |
| [05](05-mobile-remote-architecture.md) | Flutter phone ↔ agent backend architecture | **Strong for the lean stack.** Raw WebSocket (no Firebase/Supabase needed — the agent backend is already a server process), `flutter_joystick` + hand-rolled trackpad + `speech_to_text` + `flutter_tts`, `shared_preferences` with one JSON blob for the profile. Biggest risk: the phone↔backend message schema must be nailed down before either side builds deep into it. |
| [06](06-competitive-deep-dive.md) | Competitive/prior-art deep dive (beyond existing market research) | **Real prior art found — reframes the differentiation claim.** Google's "Natively Adaptive Interfaces," a May 2026 arXiv paper formalizing an almost-identical continuous capability-axis model, and the older EU GUIDE project all narrow what's safely claimable. Nothing found combines all three of (a) a live per-user profile, (b) runtime partial-modality fusion, and (c) an AI agent executing + inferring under a confirmation gate — that three-way combination, plus the explicit precision–inference coupling law, is the defensible claim. |
| [07](07-dasher-integration.md) | Dasher (github.com/dasher-project/dasher) integration | **Cite as prior art; don't integrate.** Dasher is real, decades-old, actively maintained upstream (at `GNOME/dasher` — the linked repo is a stale 2023 fork), with a WASM port that its own maintainers call "a demo, not a supported product." It's strong, specific evidence for a real gap this project hasn't addressed (free-text entry for users with no reliable speech *and* no reliable tap) — flagged as a roadmap item, not build scope. |
| [08](08-feature-ranking-auxiliary-tree.md) | Feature ranking & "auxiliary tree" generation, without an LLM per decision | **Strong.** Ranking accessibility-tree nodes by landmark role, heading level, interactivity, and link density (Readability.js/Boilerpipe-style, zero ML) mirrors exactly how real screen-reader users already navigate (~72% via headings, per WebAIM). Recommends a two-tier system: heuristic scorer first, a single narrow LLM call only when the heuristics are genuinely ambiguous. New-page detection is a solved problem (History API interception + MutationObserver fallback); "unknown" elements are resolved by watching the post-interaction effect, not classifying the element. |
| [09](09-vision-calibration.md) | Vision calibration method | **Strong for a scoped hybrid.** Real prior art exists (Peek Acuity, MNRead) but is more than a hackathon needs. Recommends 2–3 shrinking-text steps run *after* touch calibration (reusing the already-calibrated target size to avoid the vision test failing for touch-precision reasons instead of vision reasons), confirmed via a full-width tap zone or the `sounds` speech tier. |

## Cross-cutting themes worth folding back into `idea/`

- **The "no shipped product does X" pattern repeats across threads 01, 05, and 06** — independently confirms the composition/fallback/profile-driven mechanism is real differentiation, not just under-researched. Worth stating in the pitch with this evidence behind it.
- **Threads 02, 03, and 04 all converge on the same build principle**: don't build the maximal/research-grade version (full ASR personalization, fully general proactive narration, a general agent framework) — build the scoped-down version that reuses infrastructure already committed to elsewhere (the accessibility-tree + LLM pipeline), and treat the maximal version as roadmap.
- **Thread 06 changes a claim already in the pitch**: "no one models users on continuous ability axes" is no longer safe to say unqualified — a May 2026 paper already formalizes nearly the same model. The correct claim is narrower and, per that thread's finding, still fully defensible: nobody combines the profile *with* runtime fusion *and* an inferring, confirmation-gated execution agent.
- **Thread 07 exposes a real gap**, not just a citation opportunity: the current design assumes voice carries all free-text content, which leaves users with neither reliable speech nor reliable discrete tapping unaddressed — exactly Dasher's original use case. Worth a line in [idea/09-open-questions.md](../../idea/09-open-questions.md) or the roadmap.

# Research Brief 01 — Input Methods, Calibration, and Fallback Selection

Scope: evidence gathered via web search on 2026-09-05 to test technical viability of the calibration/fallback mechanism described in [02 — Core Model](../../idea/02-core-model.md), [03 — Input & Calibration](../../idea/03-input-calibration.md), and [15 — Brain Dump](../../idea/15-brain-dump.md) §15.4. Five areas requested; each closes with a feasibility verdict.

---

## 1. Existing implementations of switch-access scanning

**What real systems do.** Every mainstream switch-access system uses the same core loop: a **highlight/cursor auto-advances** through selectable items on a timer, and a **single press selects** whatever is currently highlighted (or, in row/column "group scanning," narrows a group before item-level selection). This is exactly the §3.5/§15.4 pattern already described in the docs — it is not a novel design, which is good news for build risk.

- **Android Switch Access** (Google): default auto-scan highlight duration is documented at **1 second**, with a configurable **"first-item delay"** (extra pause before the first move of a fresh screen, so the user isn't rushed) and a configurable **number of scan cycles** before auto-scan gives up and waits for manual advance. All of this lives under Settings → Accessibility → Switch Access → Settings. ([support.google.com](https://support.google.com/accessibility/android/answer/6301497?hl=en))
- **Apple Switch Control** (iOS/iPadOS/macOS): default **Auto Scanning Time is 0.5 seconds**, consistent across iOS 13–17; also exposes a separate "move repeat" and per-switch action config (select vs. move) so a single switch can do both jobs via hold-duration. ([mcmw.abilitynet.org.uk](https://mcmw.abilitynet.org.uk/how-to-use-switches-to-control-your-device-in-ios-17-on-your-iphone-or-ipad); [Orin config guide PDF](https://www.orin.com/access/docs/SwitchControlConfiguration_12-14-17.pdf))
- **Tobii Dynavox Grid 3**: scan speed/pattern configured under Settings → Access → Switches → Activation; also exposes **"Selection wait time"** and **"wait time before registering a new press"** as explicit anti-false-trigger controls — i.e. debounce is treated as a first-class tunable, not an afterthought. ([tobiidynavox.com](https://www.tobiidynavox.com/blogs/support-articles/how-do-i-adjust-switch-settings-to-filter-out-unwanted-activations)) Grid 3 is closed-source/proprietary, so it's a design reference only, not reusable code.
- **Wikipedia's "Switch access scanning" article** confirms the general taxonomy (linear vs. row-column/group scanning, visual vs. auditory scanning) and that this is standard AAC (augmentative and alternative communication) technique, decades old. ([en.wikipedia.org/wiki/Switch_access_scanning](https://en.wikipedia.org/wiki/Switch_access_scanning))

**Timing tuning pattern across all three products**: none of them ship a fixed number — all expose scan-rate as a **user-adjustable slider**, typically tuned empirically by a caregiver/therapist watching for missed vs. premature selections, with guidance like "if selections are missed, slow it down; if it feels tedious, speed it up." There is no published algorithmic auto-tuning in any of these consumer products — tuning is manual, not calibration-driven. That's actually a gap this project's calibration-score model could improve on (using the joystick/button/trackpad calibration score as a proxy for setting an initial scan rate, rather than making the user manually tune a slider).

**Reusable code**: no maintained, general-purpose open-source scanning library was found for JS or Flutter/Dart specifically. Searches for "switch-access," "scanning," and AAC-scanning GitHub topics surfaced accessibility *checkers/linters* (axe, flutter_accessibility_scanner, accessibility_tools — these audit UI for a11y compliance, unrelated to switch-scanning interaction) but not a scanning-*interaction* library. This is a "build it, small" case: the state machine itself (linear-scan timer + highlight index + single input = select) is genuinely simple — on the order of a `Timer.periodic` + an index counter — so the absence of a library is not a blocker.

**Verdict: Strong feasibility.** The pattern is well-documented, timing defaults are known (0.5–1s auto-scan, configurable first-item delay, debounce window), and the implementation is a small, well-understood state machine rather than something requiring a library. Recommend building it directly in Dart as described in §5 below, using Android's and Grid 3's debounce/first-item-delay ideas even though no code is reusable.

## 2. Joystick/trackpad calibration for motor-impaired users

**Dead zones and gain — the established two knobs.** The gaming-accessibility literature converges on the same two adjustable parameters this project's calibration would need to derive:
- **Dead zone** (ignore the innermost N% of stick travel to reject drift/tremor noise). Standard practice: measure a user's actual idle drift, then set the dead zone slightly above it. ([gpadtester.org](https://gpadtester.org/joystick-deadzone-test); [scufgaming.com](https://www.scufgaming.com/us/en/gaming/products/scuf-products/controller-calibration-dead-zones-and-stick-drift-explained/))
- **Sensitivity curve / gain** (how stick displacement maps to on-screen movement, often non-linear rather than 1:1).

**Xbox Adaptive Controller + Copilot** is the most directly relevant shipped product: it lets a user compose a custom control surface from switches/joysticks/buttons wired into one adaptive hub, with per-input remapping via the Xbox Accessories app, and "Copilot" mode which literally fuses two physical controllers (e.g. one adaptive controller plus a caregiver's standard controller) into one logical input stream. This is a strong real-world precedent for this project's Thesis B (composition/fusion of partial-ability channels), just at the hardware-input layer instead of the software-modality layer. No calibration *algorithm* is published — configuration is manual, per-user, via the companion app. ([xbox.com](https://www.xbox.com/en-US/accessories/controllers/xbox-adaptive-controller); [gameaccess.info](https://gameaccess.info/how-to-set-up-copilot-with-an-xbox-adaptive-controller-on-the-new-xbox/))

**Research base — Fitts's Law variants for motor impairment**: this is a genuinely active research area, not just a hackathon assumption.
- Modified Fitts's-Law tasks are used to **quantify tremor** by treating tremor as effectively shrinking the usable target size below its nominal size — i.e. "a tremor constant subtracted from target size" — explaining why motor-impaired users deviate from standard Fitts's-Law throughput predictions. ([researchgate.net — Fitts' Law Based Performance Metrics to Quantify Tremor](https://www.researchgate.net/publication/356710007_Fitts'_Law_Based_Performance_Metrics_to_Quantify_Tremor_in_Individuals_With_Essential_Tremor))
- Fitts's-Law target-acquisition tasks have been used directly as **BCI (brain-computer interface) and general motor-disability assessment protocols** for both able-bodied and motor-disabled populations, validating "measure via a reach-the-target task, compute an index-of-difficulty-adjusted throughput score" as a legitimate calibration methodology, not an invented one. ([PMC4075430](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC4075430/))
- The **Angle Mouse** (Wobbrock et al., CHI 2009) is the strongest single precedent: it dynamically adjusts control-display gain in real time based on how *angularly consistent* (straight-line vs. wandering) a user's cursor movement is — target-agnostic, so it needs no advance knowledge of where targets are. It improved motor-impaired pointing performance ~10% over the OS default and ~11% over "sticky icons" (a competing target-expansion technique), and shipped as free downloadable software for Windows. This is the closest existing analogue to "trackpad calibration that adapts to imprecision" and is worth citing directly in the pitch as prior art the project's trackpad fallback logic is consistent with. ([faculty.washington.edu/wobbrock — CHI'09 PDF](https://faculty.washington.edu/wobbrock/pubs/chi-09.01.pdf); [dl.acm.org/doi/10.1145/1518701.1518912](https://dl.acm.org/doi/10.1145/1518701.1518912))
- **Reflow** (arXiv 2207.07712) is a more recent (post-hoc, pixel-based) system for automatically enlarging/adjusting touch targets in existing mobile apps — relevant as evidence that "adapt the interface based on measured tap imprecision" is an active, credible line of applied research, not just this project's own idea. ([arxiv.org/pdf/2207.07712](https://arxiv.org/pdf/2207.07712))

**Verdict: Strong feasibility**, with a caveat: the *research* strongly supports doing per-user dead-zone/gain/target-size adaptation from a short calibration task — but every real product found (Xbox Adaptive Controller, gaming dead-zone tools) does this via **manual user-tuned sliders**, not an automatic algorithm from a few calibration taps. The project's plan to derive dead-zone/gain automatically from a handful of calibration attempts is more ambitious than any shipped consumer product, though well grounded in the Angle Mouse and tremor-Fitts's-Law research. Scope the calibration-driven auto-tuning modestly (e.g. use the score only to pick among 2–3 preset dead-zone/size tiers, not to compute continuous gain curves) to stay inside 30 hours.

## 3. Technical viability of the scoring formula

Formula in question: `score(method) = 0.5 × success_rate + 0.3 × (1 − time_normalized) + 0.2 × (1 − error_normalized)`

**What the literature actually supports.** ISO 9241-11 is the standard reference for usability measurement and explicitly names the three pillars this formula draws from: **effectiveness** (≈ success_rate), **efficiency** (≈ time), and **satisfaction** (not present in this formula — reasonable to drop for a machine-scored calibration test where there's no self-report). Composite usability scores that combine z-scored time, error, and success metrics under assigned weights are an established practice pattern (e.g. weighted-sum composite usability metrics reported in HCI practice), but **no single standardized formula or canonical weight-set (like 0.5/0.3/0.2) exists in the literature** — every source that discusses composite scores emphasizes that weights are chosen per-context, not derived from a universal law. So the formula's *shape* (weighted sum of normalized sub-scores) is standard practice; the *specific weights* (0.5/0.3/0.2) are a reasonable, defensible-but-arbitrary designer choice, same as most real composite-usability formulas. ([measuringu.com/iso-9241](https://measuringu.com/iso-9241/); [ScienceDirect — Usability Score overview](https://www.sciencedirect.com/topics/computer-science/usability-score))

**Concrete pitfalls to flag/fix before or during build:**

1. **Normalization needs a defined ceiling, or it silently breaks.** `time_normalized` and `error_normalized` must be normalized against *something* (a max expected time, a max expected error distance) — if that ceiling is derived from the same small calibration sample, one slow/wild attempt sets a ceiling that flatters everything else. Recommend fixing sensible hardcoded ceilings (e.g. "cap time_normalized at 5 seconds," "cap error_normalized at 50% of target distance") rather than deriving normalization bounds from the live sample.
2. **Small-N instability.** Calibration is "a handful of taps" per method — likely 2–5 attempts. A single fumbled first attempt (unfamiliarity, not true ability) can dominate the score. The SUS (System Usability Scale) literature is a useful analogue here: even that well-validated 10-item scale needs ~8 respondents for a stable score and is only accurate to ±6–10 points with 5 respondents ([measuringu.com/10-things-sus](https://measuringu.com/10-things-sus/)) — and that's *between-subject* stability, not the *within-subject, few-trials* case here. For a handful of attempts by ONE user, treat the score as a rough triage signal (good enough to rank buttons vs. joystick vs. trackpad relative to each other for one person) but not as a precise number. This matches the docs' own §3.3 framing ("relative comparison, not a fixed cutoff") — good, that design choice already defends against this pitfall.
3. **Practice/order effects.** If all three methods are tested in a fixed order, the third method benefits from the user having "warmed up." Recommend randomizing method order per calibration session, or at minimum noting this as a known limitation.
4. **Discard-vs-average outliers.** With only a few attempts, one method-specific accidental double-tap or app hiccup can swing error_normalized heavily. A trimmed mean (drop the single worst attempt) is cheap insurance and standard practice in short-trial HCI pilot work.

**Better-substantiated alternative, if literature-grounding matters more than simplicity**: **Fitts's-Law throughput** (bits/second, from index-of-difficulty ÷ movement time) is the standard, decades-validated metric for exactly this kind of "reach a target" calibration task, and is what the tremor-quantification and BCI-assessment papers above actually use rather than an ad hoc weighted sum. It would replace `time_normalized`/`error_normalized` with a single information-theoretic throughput number per attempt. This is more defensible in a paper/thesis context, but is more work to implement correctly (needs distance and target-width tracked precisely, plus the Shannon formulation) and is *harder to explain to a judge in one sentence* than "we weight success, speed, and accuracy." For a 30-hour hackathon, the current weighted-sum formula is the right trade-off; Fitts's throughput is the right roadmap answer if this becomes a real product.

**Verdict: Moderate feasibility as specified, Strong feasibility with the fixes above.** The formula's structure is legitimate and standard-practice-adjacent; the specific risk is normalization-ceiling design and small-N noise, both fixable with the concrete mitigations above without changing the formula's shape.

## 4. Existing consumer/open-source projects doing multi-method input calibration + fallback

This is the weakest-evidenced area — worth stating plainly in the pitch, because it's actually a *strength claim*: nothing quite like this appears to be shipping.

- **Ability-based design** (Wobbrock, Kane, Bigham, Pavel, Cavender — ACM TACCESS 2011, and follow-up in Communications of the ACM) is the correct *academic framing* for this whole project: "systems should adapt to what the user can do, situated ability rather than fixed disability categories," measured and adapted continuously. It is explicitly the intellectual lineage this project sits in, and is worth citing directly. It lists concrete precedent systems: **SUPPLE** (constraint-optimization UI generation based on measured dexterity/vision), the **Input Device Agent (IDA)** (observes typing performance, auto-suggests key-repeat/Sticky-Keys settings), and the **Angle Mouse** (§2 above). None of these are single-method — SUPPLE in particular generates whole UIs from a capability model, closer to this project's ambition than anything else found. ([faculty.washington.edu/wobbrock/pubs/taccess-11.pdf](https://faculty.washington.edu/wobbrock/pubs/taccess-11.pdf); [cacm.acm.org/research/ability-based-design](https://cacm.acm.org/research/ability-based-design/))
- **SUPPLE is the single closest prior system** to this project's Thesis C (task-aware, calibration-gated method selection): it takes a measured motor/vision profile and *automatically renders* the most suitable UI variant. It's a research system (University of Washington, ~2008-2010 era), not a maintained open-source product available today, and its "which UI to render" logic is XML-constraint-optimization, not the calibration-score approach here — but it is the strongest academic precedent to cite when a judge asks "has this been tried before." ([A Design Patterns Approach to Adaptive UIs — Springer](https://link.springer.com/chapter/10.1007/978-3-642-21602-2_30) discusses SUPPLE-adjacent pattern work.)
- **AutoGain** (arXiv:1611.08154) is a more recent research system extending Angle-Mouse-style gain adaptation via "submovement efficiency optimization" — evidence the research line is still active, not abandoned after Angle Mouse.
- **No shipped consumer product** (Android/iOS accessibility settings, Xbox Adaptive Controller, Grid 3, Tobii) was found that calibrates *across multiple distinct input modalities* (buttons vs. joystick vs. trackpad) and **auto-selects per-task fallback** the way this project proposes. Every shipped product found requires the user (or a caregiver/therapist) to *manually* pick and configure one input method; none run a comparative calibration test across methods and route tasks accordingly. This absence is real signal, not just a failed search — accessibility settings panels across Android, iOS, and Grid 3 are all consistently single-method-at-a-time configuration screens.

**Verdict: Weak feasibility as "already exists" — which is Strong feasibility as differentiation.** Reframe for the pitch: there is solid *academic* precedent (ability-based design, SUPPLE, Angle Mouse) validating that this general approach is sound HCI, but no evidence any shipped product does automatic multi-method calibration + per-task fallback selection the way this project proposes. That gap is exactly the pitch's "composition is the innovation" claim (§2.2 Thesis B/C) and is now evidence-backed rather than asserted.

## 5. Concrete implementation recommendation for a 30-hour Flutter build

**Current state**: `code/app/pubspec.yaml` is a fresh `flutter create` scaffold — only `cupertino_icons` and `flutter_lints` are present, no gesture/animation packages added yet.

**On-device only is correct and sufficient.** Nothing in the calibration/scoring/scanning mechanism needs a backend: calibration attempts, scores, `reachable_zone`, and the resulting method-selection logic are all pure client-side state (a `CapabilityProfile` object held in memory or persisted locally, e.g. `shared_preferences` or `hive` if persistence across app restarts is wanted). Per [15 — Brain Dump] §15.6, the phone *does* need to talk to a separate controlled computer for the demo, but that's a remote-control channel (e.g. a WebSocket/HTTP call to a companion agent), not something the calibration/input layer itself needs — keep those concerns separate so calibration logic stays trivially testable offline.

**Package recommendations, mapped to the three (four) methods:**

| Need | Recommendation | Notes |
|---|---|---|
| Buttons (discrete tap) | Plain Flutter `GestureDetector`/`InkWell` | No package needed — this is the simplest method and should not add a dependency. |
| Joystick (continuous/directional) | [`flutter_joystick`](https://pub.dev/packages/flutter_joystick) | Actively documented, supports circular/rectangular sticks, built-in "snapping," reports normalized offset (`-1..1` per axis) which maps directly onto a dead-zone/gain calibration step. Confirmed present on pub.dev with example code. |
| Trackpad (free 2D pointing / drag) | Plain `GestureDetector.onPanUpdate`/`onPanStart`/`onPanEnd` | Free-drag pointing doesn't need a package — raw pan-gesture deltas are exactly the signal needed (position, time, distance-off-target) for both the calibration test and the real interaction. |
| Scan-highlight timing (single-switch scanning, §3.5/§15.4) | `Timer.periodic` (dart:async) or an `AnimationController` with a `Ticker` | A `Timer.periodic` is simpler and sufficient for linear scan-and-highlight (advance index, wrap around, listen for the single "select" tap); an `AnimationController` is only worth it if a smooth *visual* highlight-sweep animation is wanted rather than a discrete highlight-jump. Recommend `Timer.periodic` for scope discipline — it's what Android/Apple/Grid 3's underlying mechanism conceptually is anyway (§1 above). |
| Calibration scoring / capability profile | Plain Dart class + `dart:math`, no package | The formula in §3.1 is simple arithmetic over captured (success, time, error) tuples; no ML/stats package needed. |

**What's realistically buildable in 30 hours** (aligned with [05 — Locked Scope], not fully read here but referenced by the source docs): the per-method calibration tests (buttons/joystick/trackpad, each a 2–3-attempt "reach this target" mini-game), the scoring formula with the normalization-ceiling fix from §3 above, and **one** task's ideal + fallback interaction pair, as the docs already scope. Single-switch scanning (§3.5) is a good stretch addition given §15.4's point that it's actually the *simplest* case (a `Timer.periodic` plus one button, arguably less code than the trackpad drag-to-hover fallback) — if time allows, it is cheap to add and strengthens the "we have a real answer for the floor case" pitch beat.

**No backend is needed for any of the five research areas above.** The only place a network call plausibly enters is the phone-as-remote-control channel to the demo computer (architecture doc territory, out of this brief's scope) and optionally the speech-clarity calibration (§3.1's voice test), which would use whatever on-device or cloud speech-to-text the app already integrates — not something this input-methods brief needs to specify further.

**Verdict: Strong feasibility.** Every piece needed is either built into Flutter (`GestureDetector`, `Timer.periodic`) or available as a single well-documented, low-risk package (`flutter_joystick`). No backend, no ML dependency, no exotic package risk. The main time risk is UI polish and testing the fallback interaction patterns (§3.3's 3×3 matrix, scoped down to 2 per the locked demo scope) across enough real attempts to demo confidently, not the underlying technical mechanism.
